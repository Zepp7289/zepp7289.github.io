VoidTrace实战360加固

November 17, 2026

指纹采集#

首先请上我们的老朋友360

  • 名称：com.qidian.*

  • 目标：libjiagu_vip.so

先拿到uid后编译KPM推送到设备加载然后拿到dmesg，获取目标so的指纹

static uid_t target_uid = 10297;
static char *app_name = "com.qidian.*";

从dmesg日志可以看到

[ 3433.015277] mmap pid: 28910 tgid: 28910 uid: 10297 addr: 000000745df03000 length: 1bf78 prot: 5 fd: 86 offset: 4000 ret: 000000745df03000
[ 3433.015618] mprotect pid: 28910 tgid: 28910 uid: 10297 addr: 000000745df03000 length: 1000 prot: 7
[ 3433.015632] mprotect pid: 28910 tgid: 28910 uid: 10297 addr: 000000745df03000 length: 1000 prot: 5

典型的自修改so

从这里我们拿到了mmap指纹length=0x1bf78 ，offset=0x4000

现在我们要拿到点火地址，也就是init_proc或者init_array，一般来说这些壳会在这里进行payload释放，或者检测环境等，把libjiagu_vip.so丢进IDA或者直接叫AI分析帮你找到地址

我这里懒得开IDA了，直接让AI一通分析，拿到了init_array[0]地址是0x2994AC，由于link阶段是单线程的，所以trace理论上可以完整覆盖init一直到JNI_OnLoad

参数设置#

我们这里把segment_func_offset_next设大点，覆盖掉libjiagu_vip.so的整个so，结尾由max_steps来进行，max_steps也调整到1«26使得覆盖范围尽可能多，同时也要关注手机空间，一条记录800字节，1«26就是50GB

static uint64_t segment_func_offset = 0x2994AC;
static uint64_t segment_func_offset_next = 0x2BF000;
static unsigned long max_steps = 1UL << 26;

取消掉trace的注释块，这里进行了首条记录以及trace启动

if (tmp_buf && !trace_task && !is_trace) {
    is_trace = true;
    trace_task = current;

    memcpy((char *)tmp_buf + tmp_cur_size, &regs->user_regs, sizeof(regs->user_regs));
    fpsimd_save_state_ptr((struct user_fpsimd_state *)((char *)tmp_buf + tmp_cur_size + sizeof(regs->user_regs)));
    tmp_cur_size += sizeof(regs->user_regs) + sizeof(struct user_fpsimd_state);

    task_work_add_ptr(current, &trace_start_work, true);
    pr_info("trace start pc: %px steps: %lu\n", regs->pc, trace_steps);
}

设置正确的mmap指纹

if (uid == target_uid && length == 0x1bf78 && offset == 0x4000 && !is_hook)

编译推送设备，加载后就可以启动APP了，注意顺序不能乱

启动的时候可以看到APP卡死，这是正常的，因为主线程被阻塞等待libjiagu_vip.so跑完，然而libjiagu_vip.so在被trace中，速度会变得非常慢，但是不用担心，可以去/data/data/com.qidian.*/files目录下面看trace.bin有没有在增长，同时顺便采集下dmesg日志和对应的maps

adb shell "su -c 'dmesg -C && dmesg -w'" > dmesg.log
adb shell "su -c 'cat /proc/<pid>/maps'" > maps

产物分析#

卡了一会后等trace跑完了，APP就会变的顺畅并成功启动，这时候就杀掉APP，卸载模块，拉取trace.bin到本地了

先看看trace.bin体积

-a---          2026/11/17    21:39    53687092000 trace.bin

53687092000字节，除一下单条800字节，正好是67108865条记录，1«26是67108864，所以是首条记录加上1«26条，完美

再看看dmesg.log

[ 1018.743409] trace start pc: 000000777b2a34ac steps: 0
[ 1239.426950] trace stop pc: 000000777b149fd4 steps: 67108864

可以看到trace速度还过得去吧，要知道K40是发布于6年前的老机子，存储也老化，但是依然可以做到3分多钟跑了50GB，换成更强的硬件速度还能更快

这时候就可以手动分析了，或者懒得看丢给AI也是一样的

AI结合trace，挖出了非常多的信息，节选一部分：

最后总结#

可以看到，完全没有人手工介入的情况下，AI拿到了壳完整的逻辑流，这和脱光了给人看有什么区别

首先是APK完整性校验逻辑，识别到是SM4，拿到了密钥来源是APK 签名证书的 MD5

然后是子so释放，AI直接拿到了生成算法，识别出是RC4，然后构造出了明文so，顺便和trace进行了对比验证

再往下就是dex释放和vm逻辑了，目前信息已经足够展示VoidTrace的强大，便不再展开
