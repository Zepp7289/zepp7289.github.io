VoidTrace实战梆梆加固

November 19, 2026

指纹采集#

请上御三家的最后一位，梆梆

  • 名称：cn.samsclub.*

  • 目标：libDexHelper.so

先拿到uid后编译KPM推送到设备加载然后拿到dmesg，获取目标so的指纹

static uid_t target_uid = 10308;
static char *app_name = "cn.samsclub.*";

从dmesg日志可以看到

[14426.558014] mmap pid: 9557 tgid: 9557 uid: 10308 addr: 0000007178a4d000 length: 4ca0 prot: 5 fd: 85 offset: 0 ret: 0000007178a4d000

咦，居然不是自修改，看来另有情况，继续分析

从这里我们拿到了mmap指纹length=0x4ca0 ，offset=0x0

继续丢给AI分析，拿到了init_array[0]地址是0x4780

参数设置#

老样子调整trace区间，步数，再设置正确的mmap指纹

if (uid == target_uid && length == 0x4ca0 && offset == 0x0 && !is_hook)

编译推送设备，加载后就可以启动APP了，注意顺序不能乱

采集下dmesg日志和对应的maps

adb shell "su -c 'dmesg -C && dmesg -w'" > dmesg.log
adb shell "su -c 'cat /proc/<pid>/maps'" > maps

产物分析#

等trace跑完杀掉APP，卸载模块，拉取trace.bin到本地

看看dmesg.log

[15072.990366] trace start pc: 000000717860c780 steps: 0
[15166.857456] trace stop in do_exit steps: 7292455

依然trace还在跑就被我们杀掉APP，无所谓继续丢给AI分析：

init_array[0]（OLLVM 平坦化）流程：

  1. 向后逐页扫描 0x464C457F 找自身基址 → [0x15048]
  2. dlopen("libc.so", RTLD_NOW) → dlsym(h,"sscanf") → [0x15038]
  3. 读 7 常量 → 散布到全局 0x15030~0x15088
  4. 调 worker 0x33f8（x0=0x15000 配置块）

worker 0x33f8 的完整时间线（trace 记录号）：

关键密钥写入点（trace 实证）：pc=0x3680 str w5,[x4,#0x80] 仅执行一次（记录 1137），x4=0x717861d000页, w5=0x61。 三个 XOR run：4096 / 0xf15c4 / 0x9128 字节，总迭代 1,029,868 与热点 pc 0x2bb4 计数完全吻合。

最后总结#

啪一下，AI大佬轻轻松松扒光

  1. 壳so找密钥，一个rc4一个xor

  2. 壳so解密出子so的ehdr和phdr

  3. 读取子so的的ehdr和phdr，靠这些信息mmap一块匿名内存，从壳so复制一段密文过去，继续xor解密，这就是子so代码段

  4. 壳so给子so完成链接

  5. art找壳so要JNI_OnLoad，壳一通操作，把子so的JNI_OnLoad传过去，完成偷天换日

后续子so再做一些dex解密之类的活了，不再展开
