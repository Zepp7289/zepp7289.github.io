Voidtrace在内核态进行用户态无痕Trace的KPM模块

Nov 17, 2026

VoidTrace

简介

VoidTrace 是我基于 KernelPatch 开发的一个安卓 Linux 内核模块，目前已经实现了纯内核级别的线程单步 trace，用户空间基本不可见。

项目背景

单步是什么

单步（Single-step execution）是一个计算机术语：在 gdb、ptrace 等调试过程中，可以让程序一条指令一条指令地执行，同时观察每一步执行时的变量、寄存器、内存，帮助我们更好地理解程序逻辑。

为什么开发VoidTrace

用户空间的检测例如 anti frida、svc 调用、内存 crc 检测等强度越来越大，继续在用户空间和安全厂商对抗难度水涨船高。

“Never wrestle with pigs. You both get dirty and the pigs like it.”

Linux 用户空间/内核空间的设计使得我们在内核空间具有绝对的优势，所以对抗不可避免地下沉到了内核。

但是内核虽然处理了单步逻辑，使用上都要依托用户空间的 ptrace 配合，控制还是在用户空间，又回到了用户空间对抗，于是 VoidTrace 诞生，依靠强大的KernelPatch框架，一个完全在内核进行单步的KPM模块，无需用户空间干涉。

VoidTrace解决了什么问题

目前安全厂商最主要的防护手段是 OLLVM 和 VMP，即使强如 AI 在静态分析时也难以取得有效进展。然而有了 trace 就等于在迷宫里直接有了出口线路，AI 结合 trace 可以极大提高分析效率。

VoidTrace和其他QBDI-like的trace有什么区别

QBDI-like 的 trace 工作在用户空间，检测特征较多，可以预见接下来安全厂商会加大检测力度；VoidTrace 在内核空间，天然隔离。

ARM64单步原理

ARM64 上需要几个部分配合：

  • MDSCR_EL1.SS：Monitor Debug System Control Register - Software Step，作为软件单步功能的开关。只有当 MDSCR_EL1.SS == 1 时，硬件的软件单步逻辑才会生效；如果 MDSCR_EL1.SS == 0，即便 PSTATE.SS 为 1，也不会因为单步机制触发软件步进异常。
  • PSTATE.SS：Processor State - Software Step，保存了处理器当前的执行状态，置位后，异常返回到用户态时，执行一条指令就触发一次 Software Step 异常，重新陷入内核
  • 内核侧由 arch/arm64/kernel/debug-monitors.c 的 step handler 处理异常，开关函数是 user_enable_single_step() / user_disable_single_step()

传统流程中这套机制由 ptrace 驱动：tracer 调 ptrace(PTRACE_SINGLESTEP) → 内核 user_enable_single_step() → 单步异常 → 内核给 tracer 发 SIGTRAP。单步的执行在内核，但控制和通知都要经过用户空间的 tracer，同时暴露出 TracerPid、SIGTRAP、/proc/self/status 等检测点。

VoidTrace 的做法是不依赖 ptrace，直接在内核里调用 user_enable_single_step、设置 PSTATE.SS，让单步异常循环发生，同时压制信号，用户空间不可见。

硬件断点进行点火

trace 在目标函数入口精确切入，这一步称为点火。整个流程由 mmap hook 驱动：

  1. after_mmap 中对目标 uid 的 mmap 做特征指纹匹配（以 length == 0x3110000 && offset == 0x0 识别目标 so 的代码段映射），命中后记录基址 segment_addr
  2. 用 register_wide_hw_breakpoint() 在 segment_addr + segment_func_offset（目标函数入口）挂全 CPU 的执行型硬件断点（HW_BREAKPOINT_X，长度 4 字节），硬件断点不修改内存页，不留修改痕迹
  3. 注册前把 selinux_state->enforcing 置 0 绕过 SELinux 限制，注册完恢复
  4. hook 内核的 perf_bp_event()：断点命中时比对 regs->pc，等于目标函数入口即点火——记录 trace_task = current，把初始寄存器快照写入缓冲区，再通过 task_work_add() 调度 trace_start_work 在返回用户态前打开落盘文件、创建 watchdog

内核异常无限续杯顺风车

以 alioth 内核 4.19.157 源码（Xiaomi_Kernel_OpenSource-alioth-r-oss）为准，两类调试异常在内核里的完整路径如下。

单步异常（ESR_EL1.EC = 0b1100110，DBG_ESR_EVT_HWSS）：

用户态执行一条指令，触发 Software Step 异常
  → vectors → el0_dbg                       arch/arm64/kernel/entry.S:851
  → do_debug_exception()                    arch/arm64/mm/fault.c:910
      inf = debug_fault_info[DBG_ESR_EVT(esr)]   按 ESR_EL1.EC 字段分发
  → single_step_handler()                   debug-monitors.c:231
      （debug_traps_init() 经 hook_debug_fault_code(DBG_ESR_EVT_HWSS, ...) 注册）
      → reinstall_suspended_bps(regs)       hw_breakpoint.c:850   ★ VoidTrace after-hook 点
          user_mode 分支：bps_disabled / wps_disabled 时
          toggle_bp_registers() 把挂起的断点控制位重新写回 DBGBCR_ELx / DBGWCR_ELx
      → 返回值被改写为 0 → single_step_handler 直接 return 0
  → enable_da_f / ct_user_exit → ret_to_user → kernel_exit → ERET

单步异常进入内核后，single_step_handler() 的第一条语句就是调用 reinstall_suspended_bps(regs)，把之前被挂起的硬件断点重新装回 DBGBCR_ELx/DBGWCR_ELx 控制寄存器。

VoidTrace hook 了这个函数的 after：只要 current == trace_task，就

user_enable_single_step_ptr(current);
regs->pstate |= DBG_SPSR_SS;
args->ret = 0;   // 覆盖原函数返回值

即每处理完一次单步异常，把 PSTATE.SS 再置回去，eret 回用户态执行下一条指令，再次异常，循环往复，这就是"无限续杯"。

整个单步循环复用了内核原有的异常处理流程：模块自身不注册异常 handler，不修改异常向量，只在内核必经的函数上挂钩子，这就是"顺风车"。

同时每次单步异常都是一个采样点：在同一个 hook 里判断 regs->pc 是否在 trace 区间内，是则 trace_steps++ 并把寄存器快照写入缓冲区。

SVC压制防止进程感知

单步执行经过 SVC（系统调用）时，syscall-exit 路径同样会触发单步异常。此时进程被设置了 TIF_SINGLESTEP 却没有 ptracer，内核 debug-monitors 的处理是直接

force_sig_info(SIGTRAP /* sig 5 */, info /* si_code = 0 */, trace_task);

进程收到一个 SIGTRAP，默认动作是 core dump；即使进程捕获了信号，反调试逻辑也会检测到。

所以我们 hook force_sig_info()：

if (task == trace_task && sig == 5 && info->si_code == 0) {
    args->skip_origin = true;  // 不执行原函数，信号不会发出
    args->ret = 0;
}

只匹配 sig == 5 && si_code == 0（SI_USER，内核发出的 SIGTRAP），只吞掉自己单步产生的信号，不影响进程正常信号处理。

至此，进程正常运行，单步循环只在内核里发生，用户空间不可见。

异常里面的睡眠

trace 流程里几个的重活，打开落盘文件、写文件、创建/释放 PMU watchdog都是可睡眠的操作：filp_open 要走 VFS 路径解析，可能从 UFS/eMMC 读 inode 块；kernel_write 走 ext4/f2fs 日志事务和脏页回写，内部是 mutex 和等待队列；perf_event_create_kernel_counter 要拿 perf context 的 mutex。而触发它们的时机恰恰全落在不能睡眠的上下文

为什么用 task_work_add

task_work_add_ptr(current, &trace_flush_work, true);

task_work_add(task, work, notify=true) 把 callback_head 压入 task->task_works 链表并置 TIF_NOTIFY_RESUME（kernel/task_work.c:28-40）。此后异常返回路径必经的 ret_to_user（entry.S:931）检查到该 flag，走 work_pending → do_notify_resume()（signal.c:915）→ tracehook_notify_resume() → task_work_run() 执行回调。它同时满足几个条件：

  1. 进程上下文可睡眠：do_notify_resume 里 local_daif_restore(DAIF_PROCCTX)（signal.c:935）重新打开中断，调度器可用，filp_open/kernel_write/perf mutex 这些会睡眠的操作全部合法。
  2. 天然阻塞：ERET 之前，回调在"下一条用户指令执行前"跑完，flush 完再继续单步，不会造成顺序错乱。
  3. 上下文正确：current == trace_task 自己执行。filp_open 的路径解析和权限检查用的是 trace_task 的 fs_struct/cred，换成别的线程执行语义就错了；同时 trace 缓冲区是"异常上下文只写、task_work 只读"的单线程流水，天然无需加锁。

原子区间跳过

ARM64 用 LL/SC（LDXR/STXR 独占加载/存储对）实现原子操作和锁，依赖硅片上的硬件监视器 exclusive monitor：LDXR 设置监视状态，STXR 验证监视状态并返回是否成功。

单步会破坏这个机制：LDXR 后单步异常陷入内核再返回，监视状态被破坏，STXR 永远失败，重试循环永不退出，进程卡死，这是 ARM 架构手册明文规定的行为：

（1）异常返回会清除 Exclusives monitor。D1.4.4《Exception return》在异常返回的操作序列中明确列出（D1-7212 页）：

The local Exclusives monitor for the PE executing the Exception return instruction is cleared. It is IMPLEMENTATION DEFINED whether clearing the local Exclusives monitor also clears the global Exclusives monitor.

B2.12.4《Context switch support》给出同一结论（B2-340 页）：

An exception return clears the local monitor. As a result, performing a CLREX instruction as part of a context switch is not required in most situations.

这也是内核上下文切换大多不必显式执行 CLREX 的原因。

VoidTrace 的单步循环恰好是"LDXR → 单步异常进内核 → ERET → STXR"：每次重试都在区间内注入一对 exception/exception return，同时踩中两条禁区，STXR 每次都失败，重试循环退化为死循环。

VoidTrace单步异常时读回 regs->pc 处的指令，用 is_ldx_family() 判断：

(insn & 0x3FDF0000) == 0x085F0000  // LDXR 族独占加载

命中就暂时关闭单步（user_disable_single_step + 清 PSTATE.SS），让 LL/SC 整段原子区间不被打断地执行完，避免死循环。

重新接管用 PMU watchdog：perf_event_create_kernel_counter() 创建绑定 trace_task 的 RAW 性能计数INST_RETIRED事件（config = 0x08，sample_period = 32）。关闭单步的同时通过 task_work_add 打开 watchdog，此后执行 32 条指令 PMU 计数溢出，overflow handler 里恢复单步：

user_enable_single_step_ptr(current);
_task_pt_reg(current)->pstate |= DBG_SPSR_SS;
perf_event_disable_inatomic_ptr(event);  // 自禁用，下次让权时再启用

即单步和 watchdog 交替：正常区域逐条单步，原子区间放行 32 条指令由 PMU 计数，之后恢复单步。代价是原子区间内多丢 32 条指令的 trace，并且由于PMU事件窗口延迟，可能会在原子区间出口后再丢失数个指令。

手册对 LDXR 与 STXR 之间的代码要求是"越紧越好"，并给出了量化建议（B2.12.5，B2-342 页）：

The Exclusives monitor can be cleared at any time without an application-related cause, provided that such clearing is not systematically repeated so as to prevent the forward progress in finite time of at least one of the threads that is accessing the Exclusives monitor.

Implementations can benefit from keeping the LoadExcl and StoreExcl operations close together in a single thread of execution. This minimizes the likelihood of the Exclusives monitor state being cleared between the LoadExcl instruction and the StoreExcl instruction. Therefore, for best performance, Arm strongly recommends a limit of 128 bytes between LoadExcl and StoreExcl instructions in a single thread of execution.

这就是PMU事件为什么选择32条的由来，编译器会严格遵守手册，使得原子区间不超过32条指令。

ARM64同时存在数个STX相关事件，但是和CPU架构严格相关，故在此选择更为通用的INST_RETIRED。

通用寄存器和浮点寄存器缓冲区记录

每次单步异常都是一个采样点，pc 在 trace 区间内时：

trace_steps++;
memcpy((char *)tmp_buf + tmp_cur_size, &regs->user_regs, sizeof(regs->user_regs));
fpsimd_save_state_ptr((struct user_fpsimd_state *)
    ((char *)tmp_buf + tmp_cur_size + sizeof(regs->user_regs)));
tmp_cur_size += sizeof(regs->user_regs) + sizeof(struct user_fpsimd_state);
  • regs->user_regs 即 user_pt_regs：x0–x30 通用寄存器、sp、pc、pstate，一条指令的完整上下文
  • fpsimd_save_state() 保存当前 CPU 的 NEON/浮点寄存器（user_fpsimd_state，v0–v31 + fpsr/fpcr），OLLVM/VMP 大量使用向量指令，浮点寄存器里有中间值
  • 缓冲区是 vmalloc 的 100MB 内存（tmp_buf），只写内存不落盘，减少单步路径上的开销

缓冲区将满时通过 task_work_add 调度 trace_flush_work 做一次中间落盘。

缓冲区数据落盘

  • 打开：点火时的 trace_start_fn 用 filp_open 打开 /data/data/<app>/files/trace.bin，放在 app 私有目录避免被扫描。flag 带 O_KERNEL_LARGEFILE（0400000，arm64 上真正的 O_LARGEFILE），内核 filp_open 不经过 glibc，不加这个位超过 2GB 会返回 -EFBIG
  • 写入：统一用 kernel_write() 顺序写入，flush work 和 stop work 把 tmp_buf 中积累的数据写入并复位游标
  • 停止条件：pc 到达 segment_func_offset_next（trace 区间出口），或 trace_steps >= max_steps（1 << 24）。停止时 trace_stop_fn 写完残余数据、perf_event_release_kernel 释放 watchdog、filp_close 关闭文件

最终产物是一份按指令粒度排列的二进制流，每条记录为 user_pt_regs + user_fpsimd_state，配合 so 基址可以离线还原出完整的指令级执行流。

VoidTrace存在的缺点

trace 时执行速度会比正常执行慢上好几个数量级，这是无法解决的弊端，也是检测的最强手段。
