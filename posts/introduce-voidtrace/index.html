VoidTrace在内核进行无痕Trace

November 17, 2026

VoidTrace 是我基于 KernelPatch 开发的一个安卓 Linux 内核模块，目前已经实现了纯内核级别的线程单步 trace，用户空间基本不可见。

适配设备#

  • 设备名称：红米 K40
  • 设备代号：alioth
  • 内核版本：4.19.157

VoidTrace设计#

单步是什么#

单步（Single-step execution）是一个计算机术语：在 gdb、ptrace 等调试过程中，可以让程序一条指令一条指令地执行，同时观察每一步执行时的变量、寄存器、内存，帮助我们更好地理解程序逻辑。

为什么开发VoidTrace#

用户空间的检测例如 anti frida、svc 调用、内存 crc 检测等强度越来越大，对抗难度水涨船高，知名格言：

“Never wrestle with pigs. You both get dirty and the pigs like it.”

继续和安全厂商在用户空间玩耍毫无意义，我们要做的是降维打击。

Linux 用户空间/内核空间的设计使得我们在内核空间具有绝对的优势，所以猫鼠游戏不可避免地下沉到了内核。

但是内核虽然处理了单步逻辑，使用上都要依托用户空间的 ptrace 配合，控制还是在用户空间，又回到了用户空间对抗，于是 VoidTrace 诞生，依靠强大的KernelPatch框架，一个完全在内核进行单步的KPM模块，无需用户空间干涉。

VoidTrace解决了什么问题#

目前安全厂商最核心的防护手段是 OLLVM 和 VMP，即使强如 AI 在静态分析时也难以取得有效进展。然而有了 trace 就等于在迷宫里直接有了出口线路图，AI 结合 trace 可以极大提高分析效率。

VoidTrace和QBDI或者frida-gum有什么区别#

QBDI或者frida-gum工作在用户空间，检测特征较多，可以预见安全厂商会加大检测力度，VoidTrace 在内核空间，天然隔离。

VoidTrace和unidbg有什么区别#

unidbg是一个很厉害的native模拟器，我也深入使用过一段时间，但是慢慢就觉得补环境越来越难，而且随着安全厂商意识到了unidbg存在，也推出了很多反制措施，总是补不出完美的环境，VoidTrace工作在真机，我想光这一条就够了。

ARM64单步原理#

ARM64 上需要几个部分配合：

  • MDSCR_EL1.SS：Monitor Debug System Control Register - Software Step，作为软件单步功能的开关。只有当 MDSCR_EL1.SS == 1 时，硬件的软件单步逻辑才会生效；如果 MDSCR_EL1.SS == 0，即便 PSTATE.SS 为 1，也不会因为单步机制触发软件步进异常。
  • PSTATE.SS：Processor State - Software Step，保存了处理器当前的执行状态，置位后，异常返回到用户态时，执行一条指令就触发一次 Software Step 异常，重新陷入内核

传统流程中这套机制由 ptrace 驱动：tracer 调 ptrace(PTRACE_SINGLESTEP) → 内核 user_enable_single_step() → 单步异常 → 内核给 tracer 发 SIGTRAP。单步的执行在内核，但控制和通知都要经过用户空间的 tracer，同时暴露出 TracerPid、SIGTRAP、/proc/self/status 等检测点。

VoidTrace 的做法是不依赖 ptrace，直接在内核里调用 user_enable_single_step、设置 PSTATE.SS，让单步异常循环发生，同时压制信号，用户空间不可见。

硬件断点进行点火#

trace 在目标函数入口精确切入，这一步称为点火。整个流程由 mmap hook 驱动：

  1. after_mmap 中对目标 uid 的 mmap 做特征指纹匹配（以 length == 0x3110000 && offset == 0x0 识别目标 so 的代码段映射），命中后记录基址 segment_addr
  2. 用 register_wide_hw_breakpoint() 在 segment_addr + segment_func_offset（目标函数入口）挂全 CPU 的执行型硬件断点（HW_BREAKPOINT_X，长度 4 字节），硬件断点不修改内存页，不留修改痕迹，并且使用NULL作为overflow_handler，这是关键
  3. 注册前把 selinux_state->enforcing 置 0 绕过 SELinux 限制，注册完恢复
  4. hook 内核的 perf_bp_event()：断点命中时比对 regs->pc，等于目标函数入口即点火，记录 trace_task = current，把初始寄存器快照写入缓冲区，再通过 task_work_add() 调度 trace_start_work 在返回用户态前打开落盘文件、创建 watchdog

内核单步异常#

由于ARM64硬件断点设计，如果硬件断点使用NULL作为overflow_handler后，内核会帮我们调用一次单步，这个地方就是我们的切入点

以 alioth 内核 4.19.157 源码（Xiaomi_Kernel_OpenSource-alioth-r-oss）为准，单步异常在内核里的完整路径如下：

do_debug_exception()
  └─ single_step_handler()
      ├─ reinstall_suspended_bps()
      ├─ kprobe_single_step_handler()
      ├─ call_step_hook()
      ├─ send_user_sigtrap()
      │   └─ arm64_force_sig_info()
      │       └─ force_sig_info()
      └─ user_rewind_single_step()

单步异常进入内核后，single_step_handler() 的第一条语句就是调用 reinstall_suspended_bps(regs)，把之前被挂起的硬件断点重新装回 DBGBCR_ELx/DBGWCR_ELx 控制寄存器。

VoidTrace hook 了这个函数的 after：只要 current == trace_task，就

user_enable_single_step_ptr(current);
regs->pstate |= DBG_SPSR_SS;
args->ret = 0;   // 覆盖原函数返回值

即每处理完一次单步异常，把 PSTATE.SS 再置回去，返回用户态执行下一条指令，再次异常，循环往复。

整个单步循环复用了内核原有的异常处理流程：模块自身不注册异常 handler，不修改异常向量，只在内核必经的函数上挂钩子。

同时每次单步异常都是一个采样点：在同一个 hook 里判断 regs->pc 是否在 trace 区间内，是则 trace_steps++ 并把寄存器快照写入缓冲区。

SVC压制防止进程感知#

单步执行经过 SVC时，syscall-exit 路径同样会触发单步异常。此时进程被设置了 TIF_SINGLESTEP 却没有 ptracer，内核 debug-monitors 的处理是直接

force_sig_info(SIGTRAP /* sig 5 */, info /* si_code = 0 */, trace_task);

进程收到一个 SIGTRAP，默认动作是 core dump；即使进程捕获了信号，反调试逻辑也会检测到。

所以我们 hook force_sig_info()：

if (task == trace_task && sig == 5 && info->si_code == 0) {
    args->skip_origin = true;  // 不执行原函数，信号不会发出
    args->ret = 0;
}

只匹配 sig == 5 && si_code == 0（SI_USER，内核发出的 SIGTRAP），只吞掉自己单步产生的信号，不影响进程正常信号处理。

至此，进程正常运行，单步循环只在内核里发生，用户空间不可见。

异常里面的睡眠#

trace 流程里几个的重活，打开落盘文件、写文件、创建/释放 PMU watchdog都是可睡眠的操作，而触发它们的时机恰恰全落在不能睡眠的上下文，于是选择内核常用方法task_work_add：

task_work_add_ptr(current, &trace_flush_work, true);

task_work_add(task, work, notify=true) 把 callback_head 压入 task->task_works 链表并置 TIF_NOTIFY_RESUME。此后异常返回路径必经的 ret_to_user检查到该 flag，走 work_pending → do_notify_resume()→ tracehook_notify_resume() → task_work_run() 执行回调。它同时满足几个条件：

  1. 进程上下文可睡眠：do_notify_resume 里 local_daif_restore(DAIF_PROCCTX)重新打开中断，调度器可用，filp_open/kernel_write/perf mutex 这些会睡眠的操作全部合法。
  2. 天然阻塞：异常返回之前，回调在"下一条用户指令执行前"跑完，flush 完再继续单步，不会造成顺序错乱。
  3. 上下文正确：current == trace_task 自己执行。filp_open 的路径解析和权限检查用的是 trace_task 的 fs_struct/cred，同时 trace 缓冲区是"异常上下文只写、task_work 只读"的单线程流水，天然无需加锁。

原子区间跳过#

ARM64 用 LL/SC（LDXR/STXR 独占加载/存储对）实现原子操作和锁，依赖硅片上的硬件监视器 ，LDXR 设置监视状态，STXR 验证监视状态并返回是否成功。

单步会破坏这个机制：LDXR 后单步异常陷入内核再返回，监视状态被破坏，STXR 永远失败，重试循环永不退出，进程卡死。

异常返回会清除 Exclusives monitor。D1.4.4《Exception return》在异常返回的操作序列中明确列出（D1-7212 页）：

The local Exclusives monitor for the PE executing the Exception return instruction is cleared. It is IMPLEMENTATION DEFINED whether clearing the local Exclusives monitor also clears the global Exclusives monitor.

我在这里思考了很久，尝试过如下几个方案：

  1. 仿造uprobe进行指令扫描，我觉得非常不优雅，Pass。

  2. 内核代执行，也就是跳过stx由内核写入，一是会干扰正常逻辑，二是很Dirty，Pass。

  3. 在STX+4下断点，然后进异常后继续单步，这个是我深入尝试过，但是某些原子区间会出现跳转到别处导致不触发，Pass。

  4. 模仿QBDI实现一个执行流重组，太重了，Pass。

所以我决定回到最开始，既然单步会破坏原子操作，那我们就在原子操作前面关掉单步。

VoidTrace在单步异常时读回 regs->pc 处的指令，用 is_ldx_family() 判断：

(insn & 0x3FDF0000) == 0x085F0000  // LDXR 族独占加载

命中就暂时关闭单步（user_disable_single_step + 清 PSTATE.SS），让 LL/SC 整段原子区间不被打断地执行完，避免死循环。

自然而然的我们会遇到新问题，关掉的单步如何打开？

于是我想到了PMU事件，也就是内核用来进行perf的基础设施，我们可以稍加改造，就变成了一个现成的watchdog，使我们在关闭单步后，有一个进入异常的机会，继续开启单步。

原理很简单，ARM64存在一个事件，精确统计执行了多少条指令，我们可以在关闭单步时候打开事件，然后32条指令后打醒异常，然后我们继续单步，为什么是32条呢，下面会解释。

重新接管用 PMU watchdog：perf_event_create_kernel_counter() 创建绑定 trace_task 的 RAW 性能计数INST_RETIRED事件（config = 0x08，sample_period = 32）。关闭单步的同时通过 task_work_add 打开 watchdog，此后执行 32 条指令 PMU 计数溢出，overflow handler 里恢复单步：

user_enable_single_step_ptr(current);
_task_pt_reg(current)->pstate |= DBG_SPSR_SS;
perf_event_disable_inatomic_ptr(event);  // 自禁用，下次让权时再启用

即单步和 watchdog 交替：正常区域逐条单步，原子区间放行 32 条指令由 PMU 计数，之后恢复单步。代价是原子区间内多丢 32 条指令的 trace，并且由于PMU事件窗口延迟，可能会在原子区间出口后再丢失数个指令。

ARM手册对 LDXR 与 STXR 之间的代码要求是"越紧越好"，并给出了量化建议（B2.12.5，B2-342 页）：

Implementations can benefit from keeping the LoadExcl and StoreExcl operations close together in a single thread of execution. This minimizes the likelihood of the Exclusives monitor state being cleared between the LoadExcl instruction and the StoreExcl instruction. Therefore, for best performance, Arm strongly recommends a limit of 128 bytes between LoadExcl and StoreExcl instructions in a single thread of execution.

ARM64固定一条指令4字节，128字节就是32条指令，这就是PMU事件为什么选择32的由来，编译器通常来说会遵守手册，使得原子区间不超过32条指令。

ARM64同时存在数个LL/SC相关PMU事件，但是和CPU架构严格相关，故在此选择更为通用的INST_RETIRED。

通用寄存器和浮点寄存器记录#

每次单步异常都是一个采样点，pc 在 trace 区间内时：

trace_steps++;
memcpy((char *)tmp_buf + tmp_cur_size, &regs->user_regs, sizeof(regs->user_regs));
fpsimd_save_state_ptr((struct user_fpsimd_state *)((char *)tmp_buf + tmp_cur_size + sizeof(regs->user_regs)));
tmp_cur_size += sizeof(regs->user_regs) + sizeof(struct user_fpsimd_state);
  • regs->user_regs 即 user_pt_regs：x0–x30 通用寄存器、sp、pc、pstate，一条指令的完整上下文
  • fpsimd_save_state() 保存当前 CPU 的 NEON/浮点寄存器（user_fpsimd_state，v0–v31 + fpsr/fpcr），OLLVM/VMP 或者常用加密算法大量使用向量指令，浮点寄存器里有中间值
  • 缓冲区是 vmalloc 的 100MB 内存（tmp_buf），只写内存不落盘，减少单步路径上的开销

缓冲区将满时通过 task_work_add 调度 trace_flush_work 做一次中间落盘。

数据落盘#

  • 打开：点火时的 trace_start_fn 用 filp_open 打开 /data/data/<app>/files/trace.bin，放在 app 私有目录。
  • 写入： kernel_write() 顺序写入，flush work 和 stop work 把 tmp_buf 中积累的数据写入并复位游标
  • 停止条件：pc 到达 segment_func_offset_next，或 trace_steps >= max_steps。

最终产物是一份按指令粒度排列的二进制流，每条记录为 user_pt_regs + user_fpsimd_state，配合 so 基址可以离线还原出完整的指令级执行流。

VoidTrace缺点#

trace 时执行速度会比正常执行慢上好几个数量级，这是无法解决的弊端，也是最直接的检测手段。
