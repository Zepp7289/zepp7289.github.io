指纹采集#

再次请上我们的老朋友易盾

  • 名称：com.xingjiabi.*

  • 目标：libnesec.so

先拿到uid后编译KPM推送到设备加载然后拿到dmesg，获取目标so的指纹

static uid_t target_uid = 10299;
static char *app_name = "com.xingjiabi.*";

从dmesg日志可以看到

[ 3368.313554] mmap pid: 25109 tgid: 25109 uid: 10299 addr: 00000071e9657000 length: c4000 prot: 5 fd: 88 offset: 0 ret: 00000071e9657000
[ 3368.323639] mmap pid: 25109 tgid: 25109 uid: 10299 addr: 00000071e9657000 length: c3000 prot: 7 fd: 89 offset: 0 ret: 00000071e9657000

又是典型的自修改so，而且有点意思啊，居然mmap了两次，第二次使用第一次的地址

从这里我们拿到了mmap指纹length=0xc4000 ，offset=0x0

继续丢给AI分析，拿到了init_array[0]地址是0xd9464

参数设置#

老样子我们这里把segment_func_offset_next设大点，结尾由max_steps来进行，这次就用默认max_steps = 1 « 24 吧

static uint64_t segment_func_offset = 0xD9464;
static uint64_t segment_func_offset_next = 0x101000;

取消掉trace的注释块

if (tmp_buf && !trace_task && !is_trace) {
    is_trace = true;

    memcpy((char *)tmp_buf + tmp_cur_size, &regs->user_regs, sizeof(regs->user_regs));
    fpsimd_save_state_ptr((struct user_fpsimd_state *)((char *)tmp_buf + tmp_cur_size + sizeof(regs->user_regs)));
    tmp_cur_size += sizeof(regs->user_regs) + sizeof(struct user_fpsimd_state);

    task_work_add_ptr(current, &trace_start_work, true);

}

if (uid == target_uid && length == 0xc4000 && offset == 0x0 && !is_hook)

产物分析#

等trace跑完杀掉APP，卸载模块，拉取trace.bin到本地

先看看trace.bin体积

-a---          2026/11/18    12:21     9784743200 trace.bin

9784743200/800=12230929条记录，没跑完

再看看dmesg.log

[ 5077.529906] trace start pc: 00000071e9729464 steps: 0
[ 5102.188829] trace stop in do_exit steps: 12230928

应该是trace还在跑就被我们杀掉APP导致断掉了，无所谓反正信息基本拿到了

继续丢给AI分析，AI这么强大要多加利用

AI跑了一会出内容了，看看咋样：

init[0] @ 0xd9464（idx 0–56,597，约 5.6 万条）—— 环境侦察

入口本体只有 37 条指令，全是编译期定死的不透明谓词（mov x0,#0x94 之类的常量运算 + tbz 恒真），最后尾调 0xe14a0 干活。真正做的事按 trace 顺序：

  1. dlopen(“libc.so”, RTLD_NOW) @189 → dlsym 拿 __system_property_get @431 → dlclose @438，结果缓存在 base+0xefae0。不靠 PLT/GOT 拿 libc 函数，防 hook；
  2. 读 ro.build.version.sdk @770 → atoi @772 → 33（Android 13），存起来决定后续行为分支；
  3. mmap 一页 RWX 探针页 @796 → 0x72a2e6e000，随即 mprotect 回 RX @812——埋一个“探针”；
  4. 逐行解析 /proc/self/maps：fgets×1518 + sscanf×1518（格式 “%lx-%lx %4s %*x…"），校验两条规则——libc mmap 区必须可执行、探针页必须存在且可执行（计数器 w27=2 ✓）。目的：检测 maps 是否被篡改/隐藏 （rootkit、Zygisk、内存马）。本次判定正常，状态字 0xe130 未写；
  5. 收尾 sysconf(getpagesize) + munmap 探针页 + fclose。

init[1] @ 0xd9508（idx 56,598–76,997，20,400 条）—— 基础设施 + 符号修复

让壳摆脱 linker，建立自己的运行时：

  1. x22 = base+0xf1068（全局上下文，之后所有阶段共用）；
  2. bl 0xda3cc（14,507 条）= “解密→执行→再加密”循环：
    • svc 包装器 mprotect(0xe7000,0x3000,RW) @57147 → 对 8KB 块（0xe71ec）XOR 0x54 原地解密 → icache 同步 → mprotect 回 RX @61905；
    • bl 0xe71ec 执行解密块 @61993：从 GOT 把已解析的 libc 指针拷贝成 53 项派发表 @0xefb68（dlopen/mmap/memcmp/… + 自实现 openat/close 的 svc 包装器 0xdb0b0/0xdb078/0xdb090）——之后壳调 libc 一律 走这张表，hook GOT/PLT 彻底失效；
    • 重新加密 8KB 块（mprotect RW @66417 → XOR → icache → RX @71173），不留明文；
  3. ELF 自解析（0xdc22c/0xdc57c/0xde104，771 条）：运行时读自己的 ELF 头 → 程序头 → PT_DYNAMIC，重建模块描述符（0x198 B 堆对象 malloc+memset@71189/71194）。必须在运行时做，因为节头表不在任何 PT_LOAD 里；
    • 中途 memcmp(BASE, “\x7fELF”@0xe9260, 4) 验证自身 @71347；
  4. 修符号表（0xdddd0，4,008 条）@72995：经 0xefb30 槽调 0xdd5b0，参数 (.dynsym, 57, 58, .dynstr, 0x890)：
    • 就地解密 .dynstr 前 0x890 字节（u32 ^= k; k += 偏移，k=0x56312342）；
    • 修 .dynsym[57]：st_value ^= 0x18A → 0x8EE78，st_size ^= 0x194 → 0x448——让 ART 在 dlopen 返回后能 dlsym 到真 JNI_OnLoad（名字和地址加载时都是假值，静态扫描看到的是废值）；
    • 代码里确实有信号兜底逻辑（sigaction/raise），但本次运行没走——实际只执行了旗标设置（0xe3338），这是对报告的一处修正；
  5. free(obj) @76896，ret → 交给 init[2]。

init[2] @ 0xd9bf4（idx 76,998–12,230,928，被打断）—— 苦力：把正片搬进内存

  1. A 段（~21.7 万条）：RC4 变种解密 .data 尾部 63KB
    • bl 0xdc178 @77582 把密文（base+0xf110c, 0xf6e0）拷到堆；旗标置位 + 旗标转发调驱动 0xdb5cc @77638；
    • 算法已完整还原：密文头派生 seed（CRC 多项式 0x53B20C96 → seed=0xb94902cf，@0xdb4f0 x2 实测命中）→ RC4 → A[]/T4/S9 三张派生表 → 9 模式轮流异或主循环；
    • 产物 = 原始 so（加壳前）的 6 项 ELF 程序头表（phdr[5] memsz=0x33c0/align=0x4000 已用 trace 真值逐字节证实）。说明壳把真 phdr 摘下来加密藏进 .data，文件里那份是假的；
    • @295220 拆旗标（“拆兜底”）；
    • @295236 同一驱动再次被调：源 = BASE+0x190（加密正片起点），长度 0xc2280，目的 = 4MB 匿名区 0x71e9250d00——正片解密；
  2. B 段（960 万条）：LZ77 + 两级 Huffman 解压（0xe704c @2634880 起）
    • 输入 338.6KB 压缩包（0x71d4dda000，由解压器 refill 循环边解压边搬入，不是 libc 预填——修正报告）；输出先落堆，0x52cc 主体跑 31 轮（748 万条），距离=1 游程展开 185,182 次，16B 批量直出，前 5.5KB 过校验和（31,269 次×16B）；
    • 解出的 32,771 字节是合法 AArch64 代码（本次已 dump bseg_out.bin）——一段二级原生 payload；
    • 第 31 轮后被 kill，未跑完——epilogue 0xd9d14/0xd9d24 零执行，sp 再没回 linker 层。

最后总结#

在AI神力加持下，可以看到so是怎么自修复，释放payload等一些列动作，并且依靠trace拿到了算法，离线构造了二级原生 payload
